# Portfolio Project

Plan, build, test, and publish a small project you can explain in an interview.

[← Projects](README.md) | [All roadmaps](../README.md)

## 1. Start with a useful problem

- [ ] Name one person who will use it
- [ ] Describe the problem in two sentences
- [ ] List the three most important actions they need
- [ ] Decide what is explicitly out of scope
- [ ] Write one sentence describing success

Keep the first version smaller than you think it needs to be. A finished, narrow project is stronger than a wide, unfinished one.

## 2. Design the smallest working version

- [ ] Sketch the main screens or commands on paper
- [ ] Identify the data the project stores and where it lives
- [ ] Choose a stack you have already used once
- [ ] Write a short technical plan with risks
- [ ] Break the work into small, reviewable changes

## 3. Build in vertical slices

For each slice, make the thinnest end-to-end path work before adding detail.

- [ ] Add the inputs the user provides
- [ ] Add validation and useful error messages
- [ ] Persist the data if the task requires it
- [ ] Show a valid empty state, not a blank screen
- [ ] Add loading and failure states
- [ ] Check keyboard use and mobile layout

Commit after each small, coherent change. Keep the README current as you go.

## 4. Test what matters

- [ ] Unit tests for the core business logic
- [ ] Integration tests for the main workflow
- [ ] Automated tests in CI on every change
- [ ] A manual exploratory pass on the deployed version
- [ ] A test with real content rather than sample data

## 5. Document and publish

- [ ] README with the problem, features, setup, and architecture
- [ ] A short, honest list of known limitations
- [ ] A screenshot or still image of the main view
- [ ] A live deployment link
- [ ] A short retrospective: what changed and what you learned

## 6. Prepare to explain it

Be ready to answer:

- Why did you choose this problem and scope?
- What was the hardest technical decision?
- What failed the first time, and how did you debug it?
- What would you change with another week?
- How do you know the project actually works?

Add a short decision record to the README for the choice you are most likely to be asked about.

## Definition of done

A new person can open the link, understand the purpose, use the main workflow, follow the setup instructions, and see evidence that the critical behavior is tested.
